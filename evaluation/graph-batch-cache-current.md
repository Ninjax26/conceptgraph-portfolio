# Validated cross-upload graph reuse

The optional `GRAPH_BATCH_CACHE_ENABLED` setting defaults to false. It works on the free combined processor and on the separately gated graph-continuation path. Ordinary upload checkpoints still take precedence. Only selected section and relationship-recovery batches consult the shared cache, so the existing per-attempt batch cap still bounds the work.

Within one course, the next upload can reuse an identical graph request from a READY upload's current task. Each request uses deterministic batch-local source labels. The key covers ordered source text, section headings and pages, recovery instructions and concept names, the configured provider route and model versions, prompt, schemas, repair policy, context and output limits, and validator version. File names and upload IDs are excluded from the shared prompt. A hit restores the receiving upload's chunk IDs, file name, page, heading and upload ID. The request may yield a valid empty extraction. Failed, filtered, oversized or quota-limited results do not populate the shared cache. Reads verify the payload digest and graph structure, and reject unknown source labels and extraneous node fields.

A cache entry and its source-specific checkpoint commit together under the existing document or graph-job fence. Each source owns up to 48 entries of 16 KiB of serialized graph payload each. The foreign key deletes an owner's entries with its upload. A second upload that has independently validated a reusable result owns its own copy. Disabling the setting stops future reads and writes. A flag transition invalidates incompatible per-upload extraction identities. Concurrent cache misses may each generate once. Capacity here counts logical serialized payload bytes and excludes database overhead.

## Offline verification

- Six graph tests cover renamed uploads, sections and recovery, explicit empty results, quota, source ordering, metadata, model and contract changes, corrupted records, partial outputs, and payload size.
- Two Cerebras tests use mock HTTP. The adapter records valid prompt, completion and total tokens before validating response content. Missing/invalid counts remain unknown. Captured total tokens use the provider's reported value.
- Eight isolated PostgreSQL checks exercise concurrent additive schema creation against existing data, normal processing with native PDF parsing, reuse after reconnect and schema reinitialization, course isolation, stale task rejection, a graph-only job's actual two-second retry delay followed by a cache hit, bounded storage, and owner deletion cascades. The fixture uses distinct PDF files containing the same excerpt, authored generation, and doubles for object storage, vector upsert and Neo4j projection. Database restart/crash is outside this particular fixture.
- The separate private PostgreSQL continuation runner passed 48 checks, including multiprocess claiming and recovery of a killed extractor. The provider admission runner passed 10 checks, including contention, cancellation, priority and reset. The runners removed their random schemas.

Reproduce the eight new grouped checks with `python scripts/evaluate_graph_batch_cache.py --socket-dir <owned-private-test-socket> --port <port>`. It accepts the same private Unix socket contract as the existing admission fixture. The checks used local PostgreSQL 18.7. They made zero hosted model, embedding or reranking requests and used no production records. Production quota, live provider costs, Qdrant-hosted embedding usage, fleet compatibility and rollout remain unmeasured. The provider route identity describes the configured primary and eligible backups. The cache does not assert which model won a failover.
